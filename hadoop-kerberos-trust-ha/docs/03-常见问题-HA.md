# 03. 常见问题（HA 版）

## Q0. JournalNode 启动崩溃："Principal not defined in configuration"

**现象**：`docker logs jn1` 出现
`java.io.IOException: Unable to initialize WebAppContext` →
`javax.servlet.ServletException: Principal not defined in configuration`，
容器进入重启循环（`02` 等待 JN 超时）。

**原因**：JN 的 Web 服务（8480）也会初始化 SPNEGO Kerberos 过滤器，但 journalnode 配置
缺少 `dfs.web.authentication.kerberos.principal`（基础版 NN 配置里有，JN 是新增角色漏了）。

**修复**：`ha/conf/journalnode/hdfs-site.xml` 中已显式配置：
```xml
<property>
  <name>dfs.web.authentication.kerberos.principal</name>
  <value>HTTP/_HOST@EMR.1234.COM</value>
</property>
<property>
  <name>dfs.web.authentication.kerberos.keytab</name>
  <value>/etc/hadoop/jn.keytab</value>
</property>
```
同步文件后重启 JN：`docker restart jn1 jn2 jn3`，再重跑 `bash scripts/02-start-hdfs.sh`。


## Q1. 与基础版（hadoop-kerberos-trust）的部署冲突

**现象**：`docker network create` 报 `Pool overlaps with other one on this address space`，
或宿主端口 88/50070/8088 被占用。

**原因**：两套包使用相同的外部网络 `hadoop-kerberos-net`（默认网段 172.28.0.0/24）
和相同的宿主端口映射。

**处理**：
1. 同一台宿主机**只部署一套**（推荐）；
2. 或迁移网段：`export SUBNET_BASE=172.30.0`（01/02 脚本必须同值），
   端口冲突需自行修改 compose 中 `ports`。

## Q2. nn2 首次启动一直等待/报 bootstrapStandby 失败

**现象**：`namenode-a2` 日志显示 `bootstrapStandby` 报错或长时间等待对端 active。

**原因**：
- nn1 尚未成为 active（格式化后需退出安全模式，约 30-60s）；
- JN 不可达（8485 端口）；
- Kerberos 票据问题（bootstrapStandby 需先 kinit）。

**排查**：
```bash
docker logs namenode-a1 | grep -E "RPC up at|Leaving safe mode|active" | tail
docker logs namenode-a2 | tail -30
docker exec jn1 bash -c '(exec 3<>/dev/tcp/localhost/8485) 2>/dev/null && echo JN-OK'
```

**处理**：确认 nn1 已 active 后，清掉 nn2 的初始化状态重来：
```bash
docker exec namenode-a2 rm -rf /hadoop/dfs/name/current
docker restart namenode-a2
```

## Q3. 故障转移演练中 standby 未在预期时间内接管

**现象**：`docker stop` active NN 后，另一台超过 2 分钟仍未变 active。

**原因**：
- zk1 未运行或不可达（ZKFC 依赖 ZK 会话）；
- ZKFC 未启动（查看 `docker logs <nn>` 中 zkfc 相关输出）；
- 网络分区（ZK 会话超时默认约 10s，接管一般在 15s 内）。

**排查**：
```bash
docker ps | grep zk1
docker logs namenode-a2 | grep -iE "zkfc|elect|active" | tail -30
```

## Q4. 重启整套环境后状态错乱 / 想重新初始化

**场景 A：只重启容器（保留数据）**
```bash
bash scripts/00-cleanup.sh          # 注意：HA 版默认 down -v（删除数据卷）！
```
> ⚠️ 本包 00-cleanup.sh 默认 `down -v`，会删除 NameNode 元数据与 JN 编辑日志，
> 下次 02 会全新初始化（nn1 重新 format）。如需保留数据，手动执行
> `docker compose -f ha/docker-compose.yml restart`。

**场景 B：彻底重来**
```bash
bash scripts/00-cleanup.sh --purge   # 容器+数据卷+keytab 全清
bash scripts/01-init-kdc.sh          # 重新生成 keytab（必须！keytab 与 KDC 数据库强绑定）
bash scripts/02-start-hdfs.sh
```

## Q5. 内存不足 / 容器 OOM

**现象**：NN 或 JN 容器被 kill（`docker ps` 显示 EXITED，`docker logs` 尾部有
`Killed` / `OutOfMemoryError`）。

**处理**：调低堆内存（ha/docker-compose.yml 中 `HADOOP_HEAPSIZE` 环境变量）：
- NameNode：`768`（默认）→ `512`
- JournalNode：`512`（默认）→ `256`
- 也可以给 docker 加 `--memory` 限制并加大 swap。

## Q6. 跨域访问报 "Server not found in Kerberos database"

**现象**：`hdfs dfs -ls hdfs://nn1.emr.6789.com:9000/...` 报 Kerberos 相关错误。

**原因**：
- keytab / krb5.conf 未重新生成（KDC 数据库与 keytab 不匹配）→ 重新执行 01；
- 容器无法解析对端 NN 主机名 → 检查 compose 中 `extra_hosts`（.51/.52 等 IP）；
- 时钟偏差超过 5 分钟 → 所有容器已挂载 `/etc/localtime`，确认宿主时钟正确。

## Q7. 为什么跨域访问用显式地址（hdfs://nn1.emr.6789.com:9000）而不是 nameservice？

本集群的 core-site/hdfs-site 只声明本集群的 nameservice（ns1234 / ns6789），
跨域访问时目标集群的 nameservice 定义不在客户端配置中。生产环境应在客户端配置
`dfs.nameservices` 同时包含两个 nameservice 及各自 NN 地址，即可用
`hdfs://ns6789` 跨域访问并享受故障转移代理容错。最小版为降低复杂度，跨域用显式地址
（跨域互信验证不受影响，故障转移能力在本域 nameservice 上验证）。

## Q8. 为什么 HA 版把 dfs.http.policy 从 HTTPS_ONLY 改为 HTTP_ONLY？

bootstrapStandby 通过 HTTP ImageServlet 从 active NN 下载 fsimage。
HTTPS_ONLY 需要额外的 SSL 握手/证书配置，最小版为降低首次初始化失败概率改为
HTTP_ONLY（Web UI 认证仍走 SPNEGO Kerberos）。如需 HTTPS 请参考基础版的
ssl-server.xml / ssl-client.xml 与 ca/bash 证书方案。

## Q9. JournalNode 同时服务两个集群安全吗？

安全。QJM 协议按 nameservice 隔离：编辑日志存放在
`/hadoop/dfs/journal/<nameservice>/current/` 子目录，两个集群的命名空间 ID 不同，
互不干扰。JN 的 Kerberos 主体（jn/*@EMR.1234.COM）由两个集群的 NN 通过
`dfs.journalnode.kerberos.principal` 跨域访问（集群 B 走跨域换票），
与普通跨域 HDFS 访问是同一机制。

## Q10. NN 一直卡在"等待 ZooKeeper (zk1:2181)"（zk1 的 2181 不监听）

**现象**：`docker logs namenode-a1` 只有一行 `[NN:nn1] 等待 ZooKeeper (zk1:2181) ...`；
`docker logs zk1` 开头出现：
```
ERROR o.a.z.s.q.QuorumPeerConfig - Invalid configuration, only one server specified (ignoring)
WARN  o.a.z.s.q.QuorumPeerMain - Either no config or no quorum defined in config, running in standalone mode
INFO  o.a.z.s.q.QuorumPeerConfig - clientPort is not set
```
`docker exec zk1 bash -c '(exec 3<>/dev/tcp/127.0.0.1/2181) 2>/dev/null && echo OK'` 报
Connection refused。

**原因**：新版 `zookeeper:3.8` 官方镜像（3.8.6+，2026 年构建）的入口脚本在
`ZOO_SERVERS` 只有一个 server 时不生成 `clientPort`；而 ZK 3.8 会把"仅一个 server"
的配置判为非法并忽略、退回 standalone 模式 → 2181 端口不会监听。这是镜像入口脚本
行为变化，不是本包配置错误（老版本镜像没有此问题）。

**修复**：本包已内置 `ha/conf/zk/zoo.cfg`（显式 `clientPort=2181`）并挂载到
`/conf/zoo.cfg`，同时移除了 zk1 服务的 `ZOO_SERVERS` / `ZOO_MY_ID`。同步这两个文件后：
```bash
docker compose -f ha/docker-compose.yml up -d --force-recreate zk1
# 等 10-20 秒后确认 2181 已监听：
docker exec zk1 bash -c '(exec 3<>/dev/tcp/127.0.0.1/2181) 2>/dev/null && echo ZK-OK'
```
出现 `ZK-OK` 后重跑 `bash scripts/02-start-hdfs.sh`（start-nn.sh 幂等，安全）。

## Q11. JN/NN 容器重启循环："failure to login: for principal: jn/jn2@EMR.1234.COM ... LoginException: Unable to obtain password from user"

**现象**：`docker ps` 中 jn2/jn3（或 namenode-*）处于 `Restarting` 循环（exit 255）；
`docker logs jn2` 尾部：
```
KerberosAuthException: failure to login: for principal: jn/jn2@EMR.1234.COM
from keytab /etc/hadoop/jn.keytab ... LoginException: Unable to obtain password from user
```
02 脚本表现为：JN 就绪检查超时，或一直"等待 NameNode RPC 就绪"（NN 版本：主体是
`nn/nn1@EMR.1234.COM`）。

**原因**：docker 内 JVM 对容器自身 IP 的反向解析（canonical hostname）不稳定，有时
返回短主机名（jn2）而非 FQDN（jn2.emr.1234.com）。`hdfs-site.xml` 中
`dfs.journalnode.kerberos.principal=jn/_HOST@EMR.1234.COM` 的 `_HOST` 被替换成短主机名
→ 守护进程用 `jn/jn2@EMR.1234.COM` 登录，但 keytab 里只有 FQDN 主体
（`jn/jn2.emr.1234.com@EMR.1234.COM`，见 01-init-kdc.sh）→ 登录失败 → JVM 退出 →
重启循环。同一机制也会命中 NameNode（`nn/nn1@EMR.1234.COM`）。同配置多次启动结果
不同（docker DNS 竞态），不是配置写错。

**修复**：`ha/conf/scripts/start-jn.sh` 与 `start-nn.sh` 已在启动守护进程前把本容器
IP→FQDN 写入 `/etc/hosts` 并断言反向解析结果（NSS `files` 优先于 docker DNS，
结果是确定性的）。
> ⚠️ 写 `/etc/hosts` 不能用 `sed -i`：它是 bind mount，`sed -i` 的 rename 覆盖会报
> `Device or resource busy` 失败（脚本里被 `|| true` 吞掉），旧行删不掉。
> 必须用 `cat 临时文件 > /etc/hosts` 原地重写（truncate+write，不 rename）。

同步脚本后重建容器再跑：
```bash
docker compose -f ha/docker-compose.yml up -d --force-recreate zk1 jn1 jn2 jn3
bash scripts/02-start-hdfs.sh
```

> 注意：不要通过往 keytab 里加短主机名主体（如 jn/jn2@EMR.1234.COM）来"绕过"——
> 客户端（NN 连 JN、DN/客户端连 NN）请求的始终是 FQDN 服务主体，守护进程必须以
> FQDN 主体登录，否则会把启动失败变成运行期认证失败。

## Q12. NN format 静默失败/重启循环："Server has invalid Kerberos principal: jn/jn3.emr.1234.com@EMR.1234.COM, expecting: jn/jn3@EMR.1234.COM"

**现象**：`docker logs namenode-a1` 反复出现 format 后即退出（exit 1，restart 循环）。
compose 环境下 format JVM 的 log4j 输出默认不进 docker logs（需
`HADOOP_ROOT_LOGGER=INFO,console` 才能看到），可见部分只有
`Formatting using clusterid: CID-xxx`；加上该环境变量后能看到尾部真实报错：

```
WARN namenode.NameNode: Encountered exception during format:
org.apache.hadoop.hdfs.qjournal.client.QuorumException: Unable to check if JNs are ready for formatting. 2 exceptions thrown:
172.28.0.13:8485: ... java.io.IOException: Couldn't set up IO streams:
java.lang.IllegalArgumentException: Server has invalid Kerberos principal:
jn/jn3.emr.1234.com@EMR.1234.COM, expecting: jn/jn3@EMR.1234.COM
```

特点：**JN 日志上看不到任何来自该容器的 QJM 流量**（format 在真正发 RPC 前就死了），
且每次重启生成新的 clusterid。

**原因**：与 Q11 同源的 `_HOST` 反向解析竞态，但发生在 **NN→JN 客户端方向**。
NN 客户端（QJM）按 `dfs.journalnode.kerberos.principal=jn/_HOST@EMR.1234.COM`
推导 JN 服务主体，`_HOST` 用 JN 地址的 **canonical hostname（反向解析结果）**
替换（`SecurityUtil.getServerPrincipal` → `addr.getCanonicalHostName()`）。compose
的 `*EXTRA_HOSTS` 曾同时包含 `172.28.0.13 jn3`（短名）与
`172.28.0.13 jn3.emr.1234.com`（FQDN）且**短名在前** → NN 容器内反解 JN 的 IP
得到短名 `jn3` → 期望主体 `jn/jn3@EMR.1234.COM`，与 keytab 中的 FQDN 主体
（`jn/jn3.emr.1234.com@EMR.1234.COM`）不匹配 → SASL 握手失败。此前"docker run
手动测试成功"是因为只 `--add-host` 了 FQDN 条目（反解得到 FQDN）。

**修复**（本包已内置，同步后重建容器）：
1. `ha/docker-compose.yml` 的 `*EXTRA_HOSTS` 已**移除 jn1/jn2/jn3 的短名条目**，
   JN 统一用 FQDN（短名解析由 Docker DNS 提供，容器名即 jn1/jn2/jn3）；
2. `ha/conf/scripts/start-nn.sh` 启动时把**每台 JN 的 IP 也重写为 FQDN 打头**
   （从 qjournal URI 解析 JN 主机名，与 Q11 同一套 `cat > /etc/hosts` 原地重写），
   并逐台断言反向解析结果，不匹配立即报错，避免静默重启循环。

```bash
docker compose -f ha/docker-compose.yml up -d --force-recreate jn1 jn2 jn3 namenode-a1
bash scripts/02-start-hdfs.sh
```

> 提示：QJM 已写入多个失败 clusterid 时建议全量重来：
> `bash scripts/00-cleanup.sh --purge` → `bash scripts/01-init-kdc.sh` →
> `bash scripts/02-start-hdfs.sh`，避免 JN 日志残留干扰判断。

## Q13. NN 在"NameNode RPC 就绪"后静默退出（exit 1）重启循环，日志无任何报错

**现象**：QJM 认证问题修复后，NN 日志正常走到 `NameNode RPC 就绪`（nn2 则走到
`首次启动：等待对端 nn1... active`）后，容器立即以 exit 1 重启，**没有任何报错输出**；
`docker inspect` 显示 `OOMKilled=false`、`Error=""`。nn1 与 nn2 死点不同，但**死点之后
紧邻的语句都是 `kinit`**。

**原因**：`bde2020/hadoop-namenode` 镜像**未预装 krb5-user**（`kinit` 二进制缺失）。
此前 format 能成功是因为 Java UGI 内部 keytab 登录不依赖 kinit 二进制；脚本里
`kinit ... || fail` 的失败信息走 stderr，而本环境容器日志对 stderr 不保证落盘 →
看起来是"静默 exit 1"。佐证：`scripts/03-verify.sh` 的 `ensure_kinit()` 就是专门给
容器补装 krb5-user 的。补充：容器内 apt 安装也不可靠（archive.debian.org 不可达时
`apt-get` 返回 100，`docker logs` 可见 `脚本异常退出 rc=100`），因此**不采用
"启动时补装 krb5-user"方案**。

**修复**（本包已内置）：
1. `start-nn.sh` **彻底移除 kinit 依赖**：format / `hdfs zkfc -formatZK` /
   `hdfs zkfc` / `hdfs namenode -bootstrapStandby` / NN 守护进程均由 JVM 用 keytab
   自登录（`SecurityUtil.login`），从不调用 kinit 二进制；
2. 主备状态查询 `nn_state()` 改用 NN Web UI 的 **JMX over HTTP**
   （`curl http://<nn>.<domain>:50070/jmx?qry=Hadoop:service=NameNode,name=FSNamesystemState`
   的 `state` 字段），Web 为 HTTP_ONLY 匿名访问，无需 TGT；
3. `fail()` 与 EXIT trap 统一走 stdout 留痕（`脚本异常退出 rc=N`），任何失败可见。

```bash
docker restart namenode-a1 namenode-a2 namenode-b1 namenode-b2
docker logs -f namenode-a1
```

> 提示：`03-verify.sh` 中需要 kinit 的手工验证命令（haadmin / hdfs dfs）在容器内
> 仍需 krb5-user，其 `ensure_kinit()` 会在验证时按需补装（网络可用时）。
> 另：`02-start-hdfs.sh` 的就绪判定已兼容脚本自身的 `NameNode RPC 就绪` 输出
> （NN 守护进程的 log4j 行在本环境不落盘）。
