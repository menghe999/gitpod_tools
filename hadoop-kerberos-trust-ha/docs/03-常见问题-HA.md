# 03. 常见问题（HA 版）

## Q1. 与基础版（hadoop-kerberos-trust）的部署冲突

**现象**：`docker network create` 报 `Pool overlaps with other one on this address space`，
或宿主端口 88/50070/8088 被占用。

**原因**：两套包使用相同的外部网络 `hadoop-kerberos-net`（默认网段 172.28.0.0/24）
和相同的宿主端口映射。

**处理**：
1. 同一台宿主机**只部署一套**（推荐）；
2. 或迁移网段：`export SUBNET_BASE=172.30.0`（01/02 脚本必须同值），
   端口冲突需自行修改 compose 中 `ports`。

## Q2. nn2 首次启动一直等待/报 bootstrapStandby 失败

**现象**：`namenode-a2` 日志显示 `bootstrapStandby` 报错或长时间等待对端 active。

**原因**：
- nn1 尚未成为 active（格式化后需退出安全模式，约 30-60s）；
- JN 不可达（8485 端口）；
- Kerberos 票据问题（bootstrapStandby 需先 kinit）。

**排查**：
```bash
docker logs namenode-a1 | grep -E "RPC up at|Leaving safe mode|active" | tail
docker logs namenode-a2 | tail -30
docker exec jn1 bash -c '(exec 3<>/dev/tcp/localhost/8485) 2>/dev/null && echo JN-OK'
```

**处理**：确认 nn1 已 active 后，清掉 nn2 的初始化状态重来：
```bash
docker exec namenode-a2 rm -rf /hadoop/dfs/name/current
docker restart namenode-a2
```

## Q3. 故障转移演练中 standby 未在预期时间内接管

**现象**：`docker stop` active NN 后，另一台超过 2 分钟仍未变 active。

**原因**：
- zk1 未运行或不可达（ZKFC 依赖 ZK 会话）；
- ZKFC 未启动（查看 `docker logs <nn>` 中 zkfc 相关输出）；
- 网络分区（ZK 会话超时默认约 10s，接管一般在 15s 内）。

**排查**：
```bash
docker ps | grep zk1
docker logs namenode-a2 | grep -iE "zkfc|elect|active" | tail -30
```

## Q4. 重启整套环境后状态错乱 / 想重新初始化

**场景 A：只重启容器（保留数据）**
```bash
bash scripts/00-cleanup.sh          # 注意：HA 版默认 down -v（删除数据卷）！
```
> ⚠️ 本包 00-cleanup.sh 默认 `down -v`，会删除 NameNode 元数据与 JN 编辑日志，
> 下次 02 会全新初始化（nn1 重新 format）。如需保留数据，手动执行
> `docker compose -f ha/docker-compose.yml restart`。

**场景 B：彻底重来**
```bash
bash scripts/00-cleanup.sh --purge   # 容器+数据卷+keytab 全清
bash scripts/01-init-kdc.sh          # 重新生成 keytab（必须！keytab 与 KDC 数据库强绑定）
bash scripts/02-start-hdfs.sh
```

## Q5. 内存不足 / 容器 OOM

**现象**：NN 或 JN 容器被 kill（`docker ps` 显示 EXITED，`docker logs` 尾部有
`Killed` / `OutOfMemoryError`）。

**处理**：调低堆内存（ha/docker-compose.yml 中 `HADOOP_HEAPSIZE` 环境变量）：
- NameNode：`768`（默认）→ `512`
- JournalNode：`512`（默认）→ `256`
- 也可以给 docker 加 `--memory` 限制并加大 swap。

## Q6. 跨域访问报 "Server not found in Kerberos database"

**现象**：`hdfs dfs -ls hdfs://nn1.emr.6789.com:9000/...` 报 Kerberos 相关错误。

**原因**：
- keytab / krb5.conf 未重新生成（KDC 数据库与 keytab 不匹配）→ 重新执行 01；
- 容器无法解析对端 NN 主机名 → 检查 compose 中 `extra_hosts`（.51/.52 等 IP）；
- 时钟偏差超过 5 分钟 → 所有容器已挂载 `/etc/localtime`，确认宿主时钟正确。

## Q7. 为什么跨域访问用显式地址（hdfs://nn1.emr.6789.com:9000）而不是 nameservice？

本集群的 core-site/hdfs-site 只声明本集群的 nameservice（ns1234 / ns6789），
跨域访问时目标集群的 nameservice 定义不在客户端配置中。生产环境应在客户端配置
`dfs.nameservices` 同时包含两个 nameservice 及各自 NN 地址，即可用
`hdfs://ns6789` 跨域访问并享受故障转移代理容错。最小版为降低复杂度，跨域用显式地址
（跨域互信验证不受影响，故障转移能力在本域 nameservice 上验证）。

## Q8. 为什么 HA 版把 dfs.http.policy 从 HTTPS_ONLY 改为 HTTP_ONLY？

bootstrapStandby 通过 HTTP ImageServlet 从 active NN 下载 fsimage。
HTTPS_ONLY 需要额外的 SSL 握手/证书配置，最小版为降低首次初始化失败概率改为
HTTP_ONLY（Web UI 认证仍走 SPNEGO Kerberos）。如需 HTTPS 请参考基础版的
ssl-server.xml / ssl-client.xml 与 ca/bash 证书方案。

## Q9. JournalNode 同时服务两个集群安全吗？

安全。QJM 协议按 nameservice 隔离：编辑日志存放在
`/hadoop/dfs/journal/<nameservice>/current/` 子目录，两个集群的命名空间 ID 不同，
互不干扰。JN 的 Kerberos 主体（jn/*@EMR.1234.COM）由两个集群的 NN 通过
`dfs.journalnode.kerberos.principal` 跨域访问（集群 B 走跨域换票），
与普通跨域 HDFS 访问是同一机制。
