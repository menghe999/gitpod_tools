# Kerberos 跨域互信原理与本方案架构

## 1. 单 Realm 下的 Kerberos 认证（回顾）

在一个 realm 内，用户访问服务的基本流程（Kerberos 5）：

```
客户端                    KDC(AS/TGS)                  服务端
  │── ① AS-REQ(用户名) ──→│                              │
  │←── ② TGT(用KDC密钥加密)─│                              │
  │── ③ TGS-REQ(TGT+服务)─→│                              │
  │←── ④ 服务票据(ST)──────│                              │
  │── ⑤ AP-REQ(ST) ────────────────────────────────→     │
  │←──────────────────────────────────── ⑥ 服务响应 ──────│
```

- ①-②：客户端向认证服务器（AS）拿**票据授权票据 TGT**；
- ③-④：用 TGT 向票据授权服务器（TGS）申请访问具体服务的**服务票据 ST**；
- ⑤-⑥：凭 ST 访问服务，服务端用自己 keytab 中的密钥解密验证。

大数据组件（HDFS/YARN）接入时，就是给每个服务（nn/dn/rm/nm/HTTP）创建 principal 并
导出 keytab，服务启动时 `kinit` 登录；用户则用自己的 principal 认证后访问。

## 2. 跨域互信（Cross-Realm Trust）要解决什么

两个独立 realm（如 `EMR.1234.COM` 与 `EMR.6789.COM`）各自有自己的 KDC 和用户。
`test@EMR.1234.COM` 想访问集群 B 的 `nn/namenode.emr.6789.com@EMR.6789.COM` 时，
realm A 的 KDC 无法直接为 realm B 的服务签发服务票据——它俩"不认识"。

**跨域互信** 让两个 realm 建立信任：realm A 的 KDC 为用户签发一张
**跨域 TGT**（`krbtgt/EMR.6789.COM@EMR.1234.COM`），用户凭它到 realm B 的 KDC
换取服务票据。

```
test@EMR.1234.COM 访问集群B 的流程：
┌─ realm A (EMR.1234.COM) ─┐        ┌─ realm B (EMR.6789.COM) ─┐
│ ① AS 认证拿本域 TGT        │        │                          │
│ ② TGS: 用本域TGT换 跨域TGT │        │                          │
│    krbtgt/EMR.6789.COM@   │        │                          │
│    EMR.1234.COM           │──③──→  │ ④ TGS: 用跨域TGT换 服务票据│
│    (kdc1 签发)            │        │    nn/namenode.emr.6789. │
│                          │        │    com@EMR.6789.COM       │
│                          │──⑤──→  │                          │
│                          │        │ ⑥ 凭服务票据访问 NN       │
└──────────────────────────┘        └──────────────────────────┘
```

### 2.1 互信成立的两个必要条件

1. **每个 KDC 数据库中都存在两个方向的 krbtgt principal，且密钥一致**：
   - `krbtgt/EMR.6789.COM@EMR.1234.COM`（realm A 用来签发跨域 TGT）
   - `krbtgt/EMR.1234.COM@EMR.6789.COM`（realm B 用来验证跨域 TGT）
   
   realm A 签发的跨域 TGT 必须能被 realm B 用**同一个密钥**解开，所以两个 KDC 上
   都要创建这两个 principal，并且密码一致（本方案统一 `123456`）。

2. **客户端 krb5.conf 同时知道两个 realm，并声明互信路径**：
   ```
   [realms]
    EMR.1234.COM = { kdc = kdc1; admin_server = kdc1 }
    EMR.6789.COM = { kdc = kdc2; admin_server = kdc2 }

   [capaths]                      # "." 表示两 realm 直接互信
   .EMR.1234.COM = { EMR.6789.COM = . }
   .EMR.6789.COM = { EMR.1234.COM = . }
   ```

## 3. 本方案组件与拓扑

| 组件 | 容器 | realm | 固定 IP | 作用 |
|---|---|---|---|---|
| KDC 1 | kdc1 | EMR.1234.COM | 172.28.0.2 | 集群 A 的认证中心 |
| KDC 2 | kdc2 | EMR.6789.COM | 172.28.0.3 | 集群 B 的认证中心 |
| 集群 A | namenode / datanode / resourcemanager / nodemanager | EMR.1234.COM | .21 / .22 | HDFS+YARN 安全集群 |
| 集群 B | namenode1 / datanode1 | EMR.6789.COM | .31 / .32 | HDFS 安全集群 |

- 所有容器位于同一个 Docker 网络 `hadoop-kerberos-net`（默认 172.28.0.0/24，
  与现有网络冲突时可通过环境变量 `SUBNET_BASE` 整体迁移，如
  `SUBNET_BASE=172.30.0 bash scripts/01-init-kdc.sh`，`02` 也需同样设置）；
- 双 KDC 由**同一个镜像模板**构建，`start-kdc.sh` 通过环境变量动态生成各自的
  krb5.conf，避免维护两套镜像；
- kdc2 端口映射到宿主 89/750，避免与 kdc1（88/749）冲突；容器间互访仍走 88。

## 4. 关键配置解读

### 4.1 principal 命名（HDFS/YARN 服务）

| principal | 用途 | keytab 文件 |
|---|---|---|
| `nn/namenode.emr.1234.com` | NameNode RPC | nn.keytab |
| `HTTP/namenode.emr.1234.com` | NameNode Web UI (SPNEGO) | nn.keytab（与 nn 合并导出） |
| `dn/datanode.emr.1234.com` | DataNode RPC | dn.keytab |
| `HTTP/datanode.emr.1234.com` | DataNode Web UI | dn.keytab |
| `rm/resourcemanager.emr.1234.com` | ResourceManager | rm.keytab |
| `nm/nodemanager.emr.1234.com` | NodeManager | nm.keytab |
| `test` | 本地测试用户（跨域演示） | test.keytab |

集群 B 完全对称（域名换成 `.emr.6789.com`，测试用户为 `test1`）。

### 4.2 core-site.xml（安全认证 + 跨域用户映射）

```xml
hadoop.security.authentication = kerberos
hadoop.security.authorization  = true
hadoop.security.auth_to_local  = RULE:[1:$1@$0](^.*@EMR.1234\.COM$)...
                                 RULE:[2:$1@$0](^.*@EMR.1234\.COM$)...
                                 RULE:[1:$1@$0](^.*@EMR.6789\.COM$)...
                                 RULE:[2:$1@$0](^.*@EMR.6789\.COM$)...
                                 DEFAULT
```

`auth_to_local` 将两个 realm 的 principal 都映射为本地用户名（去掉 `@REALM` 后缀），
跨域用户 `test@EMR.1234.COM` 才能在集群 B 上以本地用户 `test` 的身份落地。

### 4.3 hdfs-site.xml（服务 principal 绑定）

```xml
dfs.namenode.kerberos.principal   = nn/namenode.emr.1234.com@EMR.1234.COM
dfs.namenode.keytab.file          = /etc/hadoop/nn.keytab
dfs.datanode.kerberos.principal   = dn/datanode.emr.1234.com@EMR.1234.COM
dfs.datanode.keytab.file          = /etc/hadoop/dn.keytab
dfs.web.authentication.kerberos.principal = HTTP/namenode.emr.1234.com@EMR.1234.COM
dfs.data.transfer.protection      = integrity
dfs.block.access.token.enable     = true
```

### 4.4 时钟同步

Kerberos 默认允许 ±5 分钟时钟偏移。所有容器：
- `TZ=Asia/Shanghai`；
- 挂载 `/etc/localtime`、`/etc/timezone`、`/dev/pts`；
- 若时钟漂移超过阈值，`kinit` 会报 `Clock skew too great`（见 FAQ）。

## 5. 为什么 keytab 必须在部署时生成而不是随包分发

KDC 数据库（`kdb5_util create`）每次全新创建，master key 与各 principal 的密钥都
是新建的。仓库里无法预置"有效"的 keytab（旧 keytab 对不上新数据库），因此本方案
把 principal 创建与 keytab 导出全部自动化进 `scripts/01-init-kdc.sh`，部署者拿到
目录后一键执行即可，这也是本工具能"发给别人就能跑"的关键。
