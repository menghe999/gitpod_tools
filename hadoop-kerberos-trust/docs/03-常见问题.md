# 常见问题（FAQ）

## 1. 环境与镜像类

### Q1.1 拉取 centos:7 / bde2020 镜像失败
- 检查 Docker 是否能访问 Docker Hub；国内环境建议配置 registry mirror（如
  `https://docker.m.daocloud.io` 等），修改 Docker daemon 的 `registry-mirrors` 后重启 Docker。
- bde2020 镜像较大（每个约 1GB+），耐心等待或使用镜像加速。

### Q1.2 构建 KDC 镜像时 yum 安装失败
- KDC 构建依赖 `vault.centos.org`（见 `kerberos/custom-repo/CentOS-Base.repo`）。
  若该域名不可达，请换成可用的 centos 7 源（如阿里云
  `http://mirrors.aliyun.com/centos-vault/7.9.2009/...`）后重新 `docker compose up -d --build`。
- 也可在 `Dockerfile` 中给 `yum install` 加 `--setopt=timeout=60 --setopt=retries=5` 提升健壮性。

### Q1.3 提示 docker compose 命令不存在
- 使用老版本 `docker-compose`（Python 版）时，把脚本/命令里的 `docker compose` 换成
  `docker-compose` 即可（本项目脚本已自动兼容两种写法）。
- 网络自定义 `name:` 语法需要 docker-compose ≥ 1.29，建议直接升级到 docker compose v2。

### Q1.4 启动报 "failed to create network hadoop-kerberos-net: Pool overlaps with other one on this address space"
- **原因**：默认网段 `172.28.0.0/24` 与宿主机上某个已存在的 Docker 网络地址段重叠。
  Docker 不允许两个网络占用同一地址空间。常见于：
  - 同一台机器之前跑过本包或原项目 gitpod_tools（原项目 basic/advance 用的
    `172.20.0.0/16`、`172.20.0.0/24` 与本包默认网段撞车）；
  - 其他项目/容器网络占用了该网段。
- **排查**（找出占用网段的网络）：
  ```bash
  docker network ls
  for n in $(docker network ls -q); do
    docker network inspect "$n" --format '{{.Name}}  {{range .IPAM.Config}}{{.Subnet}}{{end}}'
  done
  ```
- **修复方式一（推荐，无需删旧环境）**：把本包整体迁移到空闲网段，
  同一终端内设置环境变量后再依次执行 01/02/03：
  ```bash
  export SUBNET_BASE=172.30.0        # 换成上面排查出的空闲网段前 3 段
  bash scripts/01-init-kdc.sh
  bash scripts/02-start-hdfs.sh
  bash scripts/03-verify.sh
  ```
- **修复方式二（确认旧网络无用后删除）**：
  ```bash
  docker network rm <冲突网络名>      # 例如 advance_kerberos-net / gitpod_tools_mynet
  docker ps -a                        # 若还有残留容器一并清理
  bash scripts/01-init-kdc.sh
  ```
- 注意：`SUBNET_BASE` 只影响容器间通信，`krb5.conf` 内部使用主机名
  （kdc1/kdc2），迁移网段无需改动任何 Kerberos 配置。

## 2. 部署流程类

### Q2.1 01-init-kdc.sh 卡在"等待 KDC 就绪"
- 查看 `docker logs kdc1`：如果 kdc1 反复重启，多半是 yum/镜像问题（见 Q1.2）；
- 确认端口 88/749 未被占用：`lsof -i :88`；冲突时修改 `kerberos/docker-compose.yml`
  的 ports 映射。

### Q2.2 忘记先执行 01 直接执行 02
- 02 脚本会预检并提示 `缺少 hdfs/kerberos/xxx，请先执行 scripts/01-init-kdc.sh`。
  先跑 01 即可。

### Q2.3 重复执行 01 安全吗
- 安全。脚本幂等：`addprinc` 对已存在的 principal 会报 "already exists" 并被忽略
  （密钥保持不变），keytab 会先删除再重新导出覆盖。
- 注意：若 HDFS 容器已经在运行，重新执行 01 后 keytab 已变化，需要重启 HDFS 容器
  才能加载新 keytab（`bash scripts/02-start-hdfs.sh` 重启或 `docker restart`）。

### Q2.4 01 脚本第 3 步报 "kadmin.local: Principal xxx does not exist" 且 chmod 找不到 keytab
- **原因**：部分 krb5 版本中 `kadmin.local -q "getprinc <不存在的principal>"` 打印
  错误但返回退出码 0，导致旧版脚本的"存在性检查"失效，`addprinc` 从未执行，
  principal 没建出来，随后 `xst` 导出 keytab 全部失败。
- **修复**：脚本已改为不依赖 kadmin 退出码——`addprinc` 无条件执行（已存在则忽略），
  导出后逐个校验 keytab 文件非空，失败会明确报错。**直接重新执行**
  `bash scripts/01-init-kdc.sh` 即可（KDC 容器无需重建，会补齐 principal 并重新导出）。

## 3. 验证失败类

### Q3.1 kinit 报 "Clock skew too great"
- Kerberos 允许 ±5 分钟时钟偏移。检查：
  ```bash
  docker exec kdc1 date && docker exec namenode date
  ```
  若不一致，确认宿主系统时间正确，然后 `docker restart kdc1 kdc2 namenode namenode1`
  让挂载的 `/etc/localtime` 生效。

### Q3.2 kinit 报 "Client not found in Kerberos database"
- 说明 `test`/`test1` principal 未创建。重新执行 `bash scripts/01-init-kdc.sh`。

### Q3.3 本域访问成功，跨域访问失败（`Server not found in Kerberos database` 等）
按顺序排查：

1. **跨域 TGT 是否可获取**：在 namenode 容器执行
   ```bash
   kvno krbtgt/EMR.6789.COM@EMR.1234.COM
   ```
   失败则说明互信未建立——检查 kdc1/kdc2 上两个 krbtgt principal 是否存在且密码一致：
   ```bash
   docker exec kdc1 kadmin.local -q "getprinc krbtgt/EMR.6789.COM@EMR.1234.COM"
   docker exec kdc2 kadmin.local -q "getprinc krbtgt/EMR.1234.COM@EMR.6789.COM"
   ```
2. **krb5.conf 是否含两个 realm + capaths**：
   ```bash
   docker exec namenode cat /etc/krb5.conf
   ```
   确认有 `[realms]` 两段、`[domain_realm]` 两段、`[capaths]` 两段。
3. **目标主机名能否解析**：
   ```bash
   docker exec namenode getent hosts namenode.emr.6789.com
   ```
   依赖 compose 里的 extra_hosts 或 Docker DNS，若解析不到，手动在容器
   `/etc/hosts` 加一条 `172.28.0.31 namenode.emr.6789.com`。
4. **KDC 日志**：
   ```bash
   docker exec kdc1 tail -50 /var/log/krb5kdc.log
   docker exec kdc2 tail -50 /var/log/krb5kdc.log
   ```

### Q3.4 跨域访问报 "No valid credentials provided"
- 确认已 `kinit`（`klist` 能看到票据）；
- 确认 core-site.xml 的 `hadoop.security.authentication=kerberos` 与
  `auth_to_local` 规则已生效（见 docs/01-原理说明.md §4.2）。

### Q3.5 03-verify.sh 卡在"等待 NameNode 就绪"
- 先看 `docker logs namenode` 是否已出现 `NameNode RPC up at: ...:9000`：
  - **已出现但脚本仍超时** → 旧版脚本的就绪关键字与 Hadoop 3.x 日志格式不匹配
    （3.x 打印 `RPC up at`，2.x 打印 `RPC server is running`）。已修复为同时兼容
    两种格式，并额外等待安全模式关闭（`Safe mode is OFF`）。直接重新执行
    `bash scripts/03-verify.sh` 即可（容器无需重启）；
  - 未出现 → 检查：
    - 反复打印 Kerberos 登录失败 → 检查 `/etc/hadoop/nn.keytab` 是否与 kdc1 数据库匹配
      （重新执行 01 后务必重启 HDFS 容器）；
    - 一直处于安全模式正常（首次启动约 1-3 分钟），耐心等待超时时间（360s）。

### Q3.6 安装 krb5-user 失败 / 很慢
- 依赖 `archive.debian.org`，网络不可达时换可用的 Debian stretch 源；
- krb5-user 安装后若 /etc/krb5.conf 被改写，脚本已自动备份恢复；
  手工操作时可先 `cp /etc/krb5.conf /root/krb5.conf.bak` 再安装。

## 4. 其他

### Q4.1 如何完全重置环境
```bash
bash scripts/00-cleanup.sh --purge
```
然后重新 `bash scripts/01-init-kdc.sh` 即可（KDC 数据库全新重建，keytab 重新生成）。

### Q4.2 端口占用怎么办
- KDC：`kerberos/docker-compose.yml` 中 kdc1（88/749）、kdc2（89/750）；
- HDFS：`hdfs/docker-compose.yml` 中 50070（NN Web UI）、8088（RM Web UI）；
  `hdfs/docker-compose-1.yml` 中 50080（集群 B NN Web UI）。
- 修改映射后，容器内部地址不变（如 namenode 仍监听容器内 50070），无需改配置。

### Q4.3 这些密码和 keytab 安全吗
- 不安全。密码（123456）、master 密码（master1234/master6789）都是测试值，
  keytab 也是测试凭据，仅用于本地演示，严禁用于生产环境。

### Q4.4 本工具与原始项目的关系
- 本目录整理自 github.com/menghe999/gitpod_tools 的
  `shell/kerberos/advance`（双 KDC 互信）与 `shell/hdfs`（双 HDFS 集群）部分，
  将原手册式操作自动化为一键脚本，并固定网络名、补充跨集群 hosts 解析与
  自动验证，做到"拿到目录即可部署"。
